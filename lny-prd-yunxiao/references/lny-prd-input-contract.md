# LNY-PRD 输入契约

## 1. 模块来源

`main_spec.md` 维护模块注册表。模块 ID 只作稳定来源键，模块改名时 ID 不变。

| 模块编号 | 模块名称 | 说明 |
|----------|----------|------|
| MODULE-001 | 商品 | 商品浏览与维护 |

新模块使用 `MODULE-{三位序号}`。禁止用显示名称或云效 ID 充当模块编号。

## 2. Feature 门禁事实

`feature_spec.md` 索引与 `feature/FEATURE-*.md` 基本信息同时维护：

| 字段 | 枚举或规则 |
|------|------------|
| 状态 | `draft` / `active` / `deprecated`，表示规格生命周期 |
| 评审状态 | `pending` / `reviewing` / `approved` / `blocked`，表示产品评审结论 |
| 模块编号 | 已在 `main_spec.md` 注册的 `MODULE-###` |
| 所属模块 | 显示名称，须与模块注册表一致 |

更新计划要求 Feature 为 `状态=active` 且 `评审状态=approved`；关闭计划要求 Feature 为 `状态=deprecated` 且 `评审状态=approved`。历史文档缺少评审状态时按 `pending`，不得把生命周期状态自动解释为已评审。

验收标准使用以下稳定来源关系：

| AC 编号 | 验收描述（可验证） | 关联规则 | 关联页面 | 关联接口 | 验证方式 |
|---------|-------------------|----------|----------|----------|----------|
| AC-1 | {可验证结果} | BR-1 / — | PAGE-MP-001 / 无 | API-MP-001 / 无 | UI + API / 数据校验 / 其它 |

- `关联页面` 决定 AC 投影到哪个页面交付面；`关联接口` 表示该 AC 依赖的实现契约。
- `本期开发` Feature 至少一条 AC；同一 Feature 内 AC ID 唯一，验收描述和验证方式均不得为空。`本期下线` Feature 可不保留 AC，关闭集合从上一版计划快照取得。
- 新建或修改 AC 必须填写 `关联页面` 或显式「无」。旧表缺少该列时，适配器可用单页 PRD §5 的页面/API 绑定推导；无法推导的 AC 只保留在 `TEST`，不靠验证文案猜角色。
- `验证方式` 是产品可理解的证据类型，不是可执行测试代码，也不绑定云效字段；禁止写 `FE/BE/MP/AD/PC/APP/H5/TEST` 等终端或任务面。适配器只从 PAGE/API/EXT 稳定编号投影责任，不从验证文案猜角色。

## 3. 页面调用 API

页面调用 API 按以下优先级读取：当前版本 `versions/{v}/pages_prd/**/PAGE-*.md` §5，其次根 `ui/PAGE-*.md` 的稳定接口表。每行包含接口编号、本页用途和触发时机。迭代版本允许只为新增/修改页面生成单页 PRD，因此不得因当前版本缺少未改页面的单页 PRD 而静默输出空绑定；两处都没有可识别接口表时阻塞导出。云效适配器据此给页面任务生成 `pageApiBindings`；API 的开发所有权仍归 `BE`，页面任务只通过 `dependencyRefs` 表达消费依赖。

每条 PAGE→API/EXT 绑定必须能归属到至少一个同时关联该 PAGE 和接口的 Feature；出现页面声明了接口、却没有任何 Feature 承接的情况以 `PAGE_API_OUTSIDE_FEATURE` 阻塞，禁止静默过滤。聚合页可承接多个 Feature，导出单个 Feature 时只投影该 Feature 接口集合内的绑定，不要求页面接口全集属于每个 Feature。

单页 PRD §6 以 `关联AC` 列反向保存本页承接的 AC ID，不复制 AC 正文。新建或修改的 PAGE 必须满足 `Feature AC.关联页面 ↔ PAGE §6.关联AC` 双向一致；没有该列的历史单页 PRD按兼容格式读取，后续修改时补齐。

## 4. 版本交付范围

正式落点：`versions/{v}/delivery_scope.md`。

```markdown
# 交付范围 - v1.0.0

## 1. 范围状态

> **产品经理填写说明**
> - `评审状态` 只填一个值：尚未发起评审填 `pending`；正在评审填 `reviewing`；存在阻塞、暂不能确认范围填 `blocked`；本期范围已明确且不存在未关闭问题时填 `approved`。
> - `产品确认项` 填仍未关闭且影响本期范围确认的问题数量。每关闭一项同步递减，全部关闭后改为 `0`。
> - 推荐流转：`pending` -> `reviewing` -> `approved`；评审中发现阻塞时改为 `blocked`，解除阻塞后回到 `reviewing`，重新确认后再改为 `approved`。

| 属性 | 内容 |
|------|------|
| 版本号 | v1.0.0 |
| 评审结论 | 通过 |
| 评审状态 | approved |
| 产品确认项 | 0 |

## 2. Feature 范围

> **产品经理填写说明**
> - `Feature` 填根 `feature_spec.md` 中已登记的 `FEATURE-###`；尚未确定时保留阻塞壳，不能从全部 `active` Feature 自动推断。
> - `纳入方式`：确定本期实现时填 `本期开发`；本期明确废弃并需关闭外部研发工作项时填 `本期下线`；尚未确定时填 `待确认`；其余 Feature 不保留在本表中。
> - 生命周期必须匹配：`本期开发` 对应 Feature `状态=active`，`本期下线` 对应 `状态=deprecated`；废弃只改状态并保留历史明细文件。
> - 行级 `评审状态` 与范围级使用同一组状态，但表示该 Feature 的开发或下线结论是否已经确认；只有已确认的本期 Feature 才改为 `approved`。
> - `阻塞决策` 填下方仍为 `open` 且影响该 Feature 的决策数量；相关决策关闭后同步递减，全部关闭后改为 `0`。

| Feature | 纳入方式 | 评审状态 | 阻塞决策 |
|---------|----------|----------|----------|
| FEATURE-001 | 本期开发 | approved | 0 |
| FEATURE-002 | 本期下线 | approved | 0 |

## 3. 未决决策

> **产品经理填写说明**
> - 每个待确认问题单独一行：未形成结论填 `open`，形成明确结论并已同步相关 PRD 后改为 `closed`。
> - `影响对象` 填受影响的 `FEATURE-###`；影响多个 Feature 时用逗号分隔。没有未决问题时仅保留 `| 无 | closed | 无 | 无 |`。
> - 所有决策均为 `closed` 后，才可把上方对应的 `阻塞决策` 归零；其他门禁也满足后，再将评审状态改为 `approved`。

| 决策编号 | 状态 | 问题 | 影响对象 |
|----------|------|------|----------|
| 无 | closed | 无 | 无 |
```

导出条件：新格式范围级 `评审结论=通过`、`评审状态=approved`、`产品确认项=0`；历史文件缺少 `评审结论` 时继续按其余批准事实兼容读取。Feature 行 `纳入方式` 为 `本期开发` 或 `本期下线`、`评审状态=approved`、`阻塞决策=0`；未决决策中不存在非 `closed` 项。`本期开发 + active` 映射为 `upsert`，`本期下线 + deprecated` 映射为 `close`；交叉组合必须阻塞。

`delivery_scope.md` 是版本范围事实，不复制 Feature 正文，不保存云效实际 ID、负责人或实时状态。根 Feature 规格表示当前状态，因此生命周期组合校验以当前最高版本为准；旧版本范围保持当时事实，不因后续下线而改写。历史云效计划应读取该版本已保存的 `yunxiao-plan.json`，不要用当前根规格重建旧快照。

`本期下线` 必须读取最近一个更早版本的 `versions/{previous}/yunxiao-plan.json`，按其中实际存在的 `FEATURE-###:*` 子任务集合生成 close；不得按当前 Feature 引用或当前映射策略猜测历史任务。历史 schemaVersion 1 快照缺 `operation` 时按 `upsert`，旧 TEST AC 为空不妨碍读取关闭对象；新生成计划仍执行完整 AC 门禁。没有上一版计划快照时以 `PREVIOUS_PLAN_MISSING` 阻塞，由产品/交付负责人先补齐可审阅历史快照或明确另行迁移方案。

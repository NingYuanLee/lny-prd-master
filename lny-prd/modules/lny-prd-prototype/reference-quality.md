# 原型写盘与 BUG 预防（§F–G）

### F. 中文 UTF-8 写盘纪律（工具建议）

乱码是写盘方式问题。写后跑验收，失败则整文件重写。

#### F.1 根因与正确写盘

| 现象 | 根因 | 正确做法 | 禁止 |
|------|------|---------|------|
| 页面出现 `?`/半拉中文 | StrReplace 破坏 UTF-8 多字节中文 | 整文件 UTF-8 写入；仅改 ASCII 可用 StrReplace | StrReplace 含 CJK / >3 行区块 |
| `UnicodeDecodeError: invalid continuation byte` | 文件已是无效 UTF-8 | 从同端已验收页复制再改 | `read_text(errors='replace')` 后写回 |
| PowerShell `python -c` 失败 | Windows GBK 与 UTF-8 混用 | 中文写在 `.py` 源码内（`# -*- coding: utf-8 -*-`） | `python -c "…中文…"` / Shell heredoc |
| 出现版本原型副本 | 旧流程或 Agent 自创镜像 | 只写根 `prototypes/`；历史回看用 Git commit/tag | 写 `versions/{v}/prototypes/`；根与版本目录双写 |

#### F.2 写后验收（必做）

```bash
python <skillDir>/modules/lny-prd-prototype/scripts/verify-prototype-utf8.py <prdRoot>/prototypes/MP/PAGE-MP-010.html
python <skillDir>/modules/lny-prd-prototype/scripts/verify-prototype-coverage.py <prdRoot> --version v1.0.0 --page PAGE-MP-010
node <skillDir>/modules/lny-prd-prototype/scripts/verify-prototype-browser.mjs <prdRoot> --page PAGE-MP-010
```

前两项 exit 0 才可继续；exit 1 不得交付，按 F.1 整文件重写（coverage 失败则按 G.4 补控件/跳转/COMP）。浏览器脚本检查真实渲染、离线资源、控制台、横向溢出、截图非空及常见交互；exit 1 必须修复，exit 2 仅表示宿主缺 `playwright` / `pngjs`，须披露未执行并人工预览。依赖只装在宿主或技能仓库，禁止在业务 `prdRoot` 初始化 npm。禁止未跑验收就汇报「已更新」；禁止把 `repair-*` 当常规步骤。

#### F.3 临时文件清理（交付前）

过程中可在 `prdRoot` 建辅助脚本（如 `scripts/`）、草稿、备份；**交付前必须删干净**（含空目录）。工具脚本始终跑 `<skillDir>/modules/lny-prd-prototype/scripts/…`，不要把技能包脚本永久留在业务项目。

### G. 原型 BUG 预防规则（必守）

交付前消除已知 BUG。

#### G.1 代码变更引用检查（必做）

删除或重命名函数/变量/类/id/DOM 前，先全文件搜索引用并修复：

| 变更类型 | 须搜索 |
|---------|--------|
| 删除函数 `foo()` | `foo(` |
| 删除变量/类/id | 单词边界；`getElementById` |
| `<script src>` | 须有对应 `</script>`；Network 200；Console 无 ReferenceError |
| 新增全局调用 | `assets/` 或项目脚本中有对应定义，调用名称与项目实现一致 |
| 壳层菜单超出视口 | `.proto-sidebar__nav` 有 `overflow-y: auto` |

#### G.2 状态演示按钮归位（必做）

规则见 [`reference-shell.md`](reference-shell.md) 状态演示。区分用户操作和后端模拟，具体表现由项目原型设计决定。需要状态演示时使用壳层能力，不把测试控制器误当成业务入口。

### G5.15 视觉方向实现

- PAGE 已提供 §2.4 视觉方向契约，或已在项目级设计方向中明确记录。
- 首屏视觉锚点、层级节奏、色彩语义、组件表现、素材策略和签名元素在页面中可见。
- 同一终端的页面在项目事实允许时共享品牌和交互语言。页面可以根据任务形成不同的视觉方向，不要求套用同一模板。
- 视觉方向缺失时由模型依据页面任务和项目事实做出设计决策，并在需要时记录假设。

### G5.16 基础模型视觉基线

- 首屏有明确主任务和视觉锚点，不是等权信息堆叠。
- 避免无业务理由的默认三等分卡片、全页面卡片化或单一按钮色堆叠。页面任务需要时可以采用这些形式。
- 列表、表单、详情和工作台使用匹配的页面骨架。
- 页面经过至少一次真实渲染检查，已检查层级、密度、溢出、图片比例和移动端滚动。

### G5.17 设计决策与素材可实现性

- 页面首要任务、视觉锚点、页面骨架、素材策略和响应式取舍已经明确；缺失时由技能自动补齐并记录默认假设。视觉表达可以由模型结合任务自由设计。
- 关键字体、图片、图标、边框、纹理和装饰均有来源或实现路径；不可获得的关键资产使用可替换占位并记录。
- 页面没有把整页生图当作正式结构来源；文字、组件、状态、跳转和响应式表现均由 HTML/CSS 实现。
- 生图仅用于独立视觉素材或未确定方向的探索，不能把生图中的文字、字距、尺寸和装饰自动视为可交付实现。

### G5.18 真实渲染闭环

- 页面至少经过一次浏览器真实渲染检查，并根据检查结果修正首屏主次、文字溢出、内容密度、图片比例、滚动和固定区。
- 设计方向中的核心视觉锚点和签名元素在 HTML 中仍然可见；内容变化或素材替换后页面仍保持结构稳定。设计方向可以因页面任务而变化。

### G5.19 演示级内容真实感

- 直接打开业务页即可理解主任务，不需要阅读规格说明、设计决策或验收提示。
- 默认文案和数据应服务产品演示目标。早期探索可以使用明确标注的占位数据，不把文案词汇当作原型结构硬门禁。
- 默认态在需要时覆盖真实格式的时间、金额、编号或统计值，并包含代表性长度的名称和状态。
- 空态、加载态和失败态只在对应状态下展示，并提供面向用户的状态文案和下一步操作。

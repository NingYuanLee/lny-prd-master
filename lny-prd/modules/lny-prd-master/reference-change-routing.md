# 原型反馈变更路由

产品经理经常直接对着原型提出修改。先判断反馈影响哪类事实，再选择最小写入集。不要因为反馈来自原型就只改 HTML，也不要因为改了一个间距就重跑完整规格链。

## 先问一个判定问题

**如果研发只看到这次修改后的页面，是否会实现出不同的产品行为、页面结构、数据契约或验收结果？**

- 否 → 走 A 视觉微调。
- 只改变已有控件在操作中的可见表现 → 走 B 交互表现。
- 改变分区顺序、页面组成、跳转或终端适配 → 走 C 页面结构。
- 改变业务规则、字段、权限、Feature、AC、页面归属或交付范围 → 走 D 产品事实。

如果一句反馈同时命中多类，按影响最大的类别处理。无法判断时先读取关联 `ui/PAGE`、`pages_prd`、Feature 和 API 的对应段落，不凭页面截图猜业务事实。

## 四类变更

| 类别 | 常见反馈 | 最小写入集 | 必做检查 |
|---|---|---|---|
| A 视觉微调 | 间距、留白、颜色、边框、字号、圆角、阴影、图片裁切、对齐、文案错字 | `prototypes/{终端}/PAGE-*.html`；必要时 `prototypes/.design-decisions/PAGE-*.md` | 目标页渲染、自评、UTF-8、局部浏览器检查 |
| B 交互表现 | 已有按钮的按下反馈、已有弹窗的尺寸和过渡、已有状态的视觉表现 | A 的文件 + 对应 `ui/PAGE` 或 `ui/COMP` 状态矩阵；若 ⑤ 已描述该行为，再同步 `pages_prd` 的表现段 | 受影响页 Q-P；若状态契约改变，再跑对应 Q-S |
| C 页面结构 | 增删区块、调整分区顺序、增加页面、改变跳转或终端布局 | `ui/` → `pages_prd/` → `prototypes/` 的受影响文件 | 受影响对象 Q-S、事实一致性审计、Q-P |
| D 产品事实 | 改业务规则、字段、权限、Feature、AC、接口、页面归属、交付范围 | 先改正本，再同步下游索引、明细、PAGE 和原型 | 语义检查、事实一致性审计、受影响页 Q-P；涉及范围时再走评审 |

## A 类快速路径

A 类反馈不新增版本，不修改 `main_spec`、`ui_manifest`、`api_spec`、`feature_spec`、`pages_prd` 或台账。直接修改当前原型，记录一句可复核的视觉决策，例如“把筛选栏与列表的间距从过松收紧，使首屏多显示一行结果”。

完成后只检查目标页。若渲染观察发现页面任务、交互契约或内容含义也变了，立即升级到 B、C 或 D，不继续把业务变化藏在 HTML 里。

## D 类根因同步顺序

1. 修改事实正本。
2. 搜索受影响的 ID、字段名、页面名称、路径和状态。
3. 更新索引和下游明细，不复制新的事实来源。
4. 运行 `audit-fact-consistency.py`，修复所有 `FACT_DRIFT`。
5. 只对受影响页面重跑规格和原型检查。

## 输出格式

每次原型反馈只需报告：

- 变更类别：A / B / C / D
- 受影响文件：实际路径
- 是否修改正本：是 / 否
- 检查范围：目标页或受影响对象
- 结果：完成 / 升级处理 / 待产品决策

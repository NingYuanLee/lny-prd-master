# 需求与交付范围评审协议

执行 `/lny-prd-review` 时 Read 本文件。评审员负责形成明确、可执行的拟定结论，产品负责人只需确认或指出修改项；未经确认的结论不写成批准事实。

## 1. 证据口径

每条关键判断标明依据类型：

| 类型 | 口径 |
|------|------|
| 已知事实 | 可在 PRD、版本范围、用户当前消息或明确提供的外部材料中定位 |
| 合理推断 | 由多个已知事实推出，须写明推断链与不确定性 |
| 待确认 | 缺少会改变结论的产品事实；转成具体问题，不自行补齐 |

优先使用用户问题、目标、成功指标与明确范围作为判断基准。缺少业务数据不等于需求必然不成立，但必须降低结论置信度；不得虚构访谈、市场数据、收入、成本或用户反馈。

### 1.1 版本证据层与候选范围组装

先解析目标版本，并按版本类型建立证据层：

- **首版**：根目录当前完整规格 + 用户当前消息。首版没有上一版批准基线；不得要求不存在的三类change文档。
- **非首版**：当前版本 `feature_changes.md` / `ui_changes.md` / `api_changes.md` 定义本版变化，根目录规格定义变化后的完整事实，上一semver版本 `delivery_scope.md` 与批准PAGE快照定义已发布基线。change文档不能替代完整规格，根目录也不能替代版本差异证据。

评审员负责先给候选，产品不负责从空白开始整理。按以下优先级组装，并在结论包中说明每项来源：

1. 用户在当前消息中明确指定的 Feature 与取舍。
2. 非首版目标版本 `feature_changes.md` 中新增、修改、废弃的Feature；再由 `ui_changes.md` / `api_changes.md` 反查未直接登记但实际受影响的Feature。废弃项只作为 `本期下线` 候选，不自动批准。
3. 为完成上述 Feature 不可缺少的直接依赖 Feature。
4. 已有 `delivery_scope.md` 中仍与当前事实一致的范围行。

不得把全部 active Feature 自动纳入，也不得因为台账出现就直接判定本期开发。候选之外的 active Feature 默认“不纳入本次候选”，无需逐行写进范围文件。候选事实不足时仍须给出“退回补充”结论及最小待补问题，不能要求产品先重写候选清单。

### 1.2 PAGE版本范围原子性门禁

PAGE是版本发布与开发交付的最小页面单元。对每个PAGE计算“本版受影响Feature集合”：

- 首版：该PAGE承接的全部待发布active Feature。
- 非首版：当前版本三类change文档直接登记或经PAGE/API变化反查到、且关联该PAGE的Feature。上一版已批准且本期未变化的Feature属于存量基线，不要求重复纳入。

同一PAGE的本版受影响Feature只允许**全部纳入本期范围**或**全部不纳入**，禁止部分纳入、部分不纳入。`本期开发`与`本期下线`都算已纳入本版范围；它们可以共存，但不能遗漏同页其它本版受影响Feature。

发现冲突时不得拟定“通过”，必须在结论包中选定一条修复路径：

1. 产品范围允许：留在⑧，把同页受影响Feature一并纳入后重发完整结论包。
2. 产品坚持拆分：按最早责任步骤返回②页面/交互、③数据/API、④Feature/AC中的受影响子集，拆页面、拆依赖或重划AC归属，再自动走⑤→Q-S→⑥→Q-P→⑧。

禁止通过裁剪版本快照来掩盖范围冲突；快照只能在原子性门禁通过后生成。

## 2. 评审维度

### 2.1 问题与证据

- 问题是否具体到目标用户、场景、当前障碍和影响。
- 需求是解决真实问题，还是只有功能想法。
- 支撑优先级的证据是否存在；没有证据时指出需要验证的最小假设。

### 2.2 目标与价值

- 产品目标、用户收益和“成功怎么算”是否能互相解释。
- 成功指标是否可观察，是否可能只衡量功能上线而非效果。
- 收益对象、受损对象与业务约束是否被说明。

### 2.3 范围与优先级

- 本期范围是否直接服务目标；是否混入顺手建设、未来能力或框架通用能力。
- P0/P1/P2 是否与问题严重度、时效、依赖和投入相称。
- 给出必须保留、建议删减、可延期、待确认四类范围建议；不得替用户直接改范围。

### 2.4 方案与替代

- 是否把预设实现当成唯一需求；是否存在更小验证方案或非研发替代。
- 页面、流程、接口和规则复杂度是否超出目标所需。
- 对高成本或不可逆方案，至少比较“维持现状 / 最小方案 / 当前方案”。

### 2.5 验收与效果

- AC 是否证明关键行为与异常边界，而不只是证明页面或按钮存在。
- 验收证据能否回到产品目标；上线完成和目标达成须分开。
- 成功指标缺失时可建议补充，但禁止自拟业务目标后当作既定事实。

### 2.6 依赖与风险

- 检查外部依赖、数据迁移、合规/资金/隐私影响、跨端一致性、运营承接和可逆性。
- 区分阻塞决策与一般风险；只有会改变是否做、做什么或何时做的问题进入未决决策。

### 2.7 交付范围

- `本期开发` 是否对应当前版本真正要交付的 active Feature。
- `本期下线` 是否对应明确废弃且需要关闭外部研发工作项的 deprecated Feature。
- 范围成员之间是否存在缺失依赖、互斥结论或无法独立验收的拆分。
- 同一PAGE的本版受影响Feature是否满足范围原子性；非首版须排除上一版已发布且本期未变的存量Feature后再判断。
- 范围批准必须经过产品确认；评审员负责给出明确拟定结论，但不能根据 `active`、台账完成或检查通过跳过确认。

## 3. 拟定结论口径

| 拟定结论 | 使用条件 | 确认后状态原则 |
|----------|----------|----------------|
| 通过 | 价值、范围、关键方案与验收均有充分依据，无改变范围的阻塞问题 | 对应评审状态可写 `approved` |
| 附条件通过 | 方向成立，但仍有少量须关闭的明确条件 | 保持 `reviewing`；阻塞交付的条件写 `blocked`，条件关闭后重新给出“通过”结论 |
| 退回补充 | 关键事实不足，当前无法可靠判断 | 写 `blocked` 或保持 `pending`，由结论包明确选定，不自动进入本期 |
| 不进入本期 | 价值不足、范围失焦、成本/风险明显不匹配，或有更小替代方案 | 从本期候选范围排除；不等于删除或废弃 Feature |

评审员必须选择一个档位，不得用“供产品自行判断”代替结论。证据不足时应选“退回补充”，而不是编造事实。每个结论包还须明确确认后对范围行、评审状态、确认项和未决决策的具体影响。

## 4. 评审修订循环

产品收到拟定结论后可采取两类动作：

1. **确认**：无保留采纳完整结论，进入记录模式。
2. **调整**：补充或纠正事实、改变业务约束、增删范围、修改条件，或直接质疑某项判断。

收到调整时：

- 先识别变化属于新事实、产品取舍还是单纯偏好。
- 新事实须重新核对相关证据；产品取舍须评估对目标、范围、风险和验收的连锁影响。
- 同意调整时，合并进完整修订结论；不同意时，明确说明依据与残余风险，不能只回复“坚持原结论”。
- 产品有最终决策权。若产品明确坚持与专业评审不同的取舍，结论包同时写“评审意见”和“产品拟定决议”，保留风险说明，并以产品拟定决议作为待确认、待落盘内容。
- 每次调整后都重发一份完整、自足的结论包；旧结论自动失效，只有最新一份可被确认。

## 5. 拟定结论包格式

```text
需求评审：{版本 / FEATURE / 主题}

拟定评审结论（待产品确认）
- 结论：{通过 / 附条件通过 / 退回补充 / 不进入本期}
- 置信度：高 / 中 / 低
- 核心理由：{1～3 条}

阻塞问题
#1 {会改变结论的问题；无则写“无”}

维度判断
- 问题与证据：...
- 目标与价值：...
- 范围与优先级：...
- 方案与替代：...
- 验收与效果：...
- 依赖与风险：...

范围建议
- 拟定交付范围：{FEATURE-* → 本期开发 / 本期下线 / 不纳入本期}
- PAGE原子性：{通过；或 PAGE-* 的本版受影响Feature发生范围冲突及选定修复路径}
- 必须保留：...
- 建议删减：...
- 可延期：...
- 待确认：...

确认后记录
- delivery_scope：{范围级状态、确认项、范围行和决策行的精确变化；不涉及则写“无”}
- Feature 评审状态：{FEATURE-* → approved/reviewing/blocked/pending；不涉及则写“无”}

后续动作
- #序号 → /lny-prd-feature、/lny-prd-iter、/lny-prd-ui、/lny-prd-api 或 /lny-prd-page

批准发布预览
- PAGE：{PAGE-* → 根工作源 → 页面路由 → 版本快照路径；非最终通过写“暂不发布”}

请产品回复“确认”，或直接补充事实、调整范围/条件、质疑判断。
```

只列会影响决策的内容。通过项可压缩，不要把结构完整性检查改写成评审意见。结论包必须自足，使产品无需重新组织或复述决议。

## 6. 范围决议记录协议

写入前完整读取根 `feature_spec.md` 和涉及的 `feature/FEATURE-*.md`；目标 `delivery_scope.md` 已存在时完整读取，不存在时按下方模板创建。版本目录必须已存在。

### `delivery_scope.md` 模板

仅在产品确认最新完整结论包后创建。文件记录确认后的产品决议，不是 ①/⑩ 的待填壳。

```markdown
# 交付范围 - {版本号}

## 1. 范围状态

| 属性 | 内容 |
|------|------|
| 版本号 | {版本号} |
| 评审结论 | {通过 / 附条件通过 / 退回补充 / 不进入本期} |
| 评审状态 | {approved / reviewing / blocked} |
| 产品确认项 | {非负整数} |

> `通过` 与 `不进入本期` 的确认结果使用 `approved`；`附条件通过` 使用 `reviewing` 或 `blocked`；`退回补充` 使用 `blocked`。只有 `通过` 或 `不进入本期`、确认项为 0 且无 open 决策时，⑩ 才视为评审终态。

## 2. Feature 范围

| Feature | 纳入方式 | 评审状态 | 阻塞决策 |
|---------|----------|----------|----------|
| {FEATURE-###} | {本期开发 / 本期下线} | {approved / reviewing / blocked} | {非负整数} |

> `不进入本期` 且无交付范围时，仅保留 `| 无 | — | approved | 0 |`。未纳入候选不写入本表。

## 3. PAGE 发布映射

| PAGE | 终端 | 工作源 | 页面路由 | 快照路径 |
|------|------|--------|----------|------------|
| {PAGE-MP-001} | {MP} | {pages_prd/MP/PAGE-MP-001.md} | {pages/index/index} | {versions/v1.0.0/pages_prd/MP/pages/index/index/PAGE-MP-001.md} |

> 本表只在最终“通过”确认且PAGE版本范围原子性门禁通过后写入，只列本期批准范围涉及的业务页面。快照按完整页面路由投影，文件名保持PAGE编号；不得包含 `_shell`。非首版快照可保留上一版已批准且本期未变的存量行为，但不得通过裁剪本版受影响Feature来绕过范围原子性。

## 4. 未决决策

| 决策编号 | 状态 | 问题 | 影响对象 |
|----------|------|------|----------|
| {DECISION-### / 无} | {open / closed} | {问题 / 无} | {FEATURE-### / 无} |
```

### 6.1 可写内容

- 范围级 `评审状态` 与 `产品确认项`。
- 范围级 `评审结论`。
- Feature 范围行的增删、`纳入方式`、行级 `评审状态` 与 `阻塞决策`。
- 最终“通过”时的PAGE发布映射，以及由该映射生成的只读版本快照。
- 未决决策的新增、问题修订、影响对象与 `open/closed` 状态。

保留文件标题、产品经理填写说明、表结构和与本次决议无关的历史内容。一次完整读取、一次整块更新，禁止逐行碎片化替换。

### 6.2 确认与写入门禁

- Feature 必须已在根 `feature_spec.md` 登记。
- `本期开发` 只能对应 `active`；`本期下线` 只能对应 `deprecated`。
- PAGE版本范围原子性必须通过；冲突未解决时禁止记录“通过”、写PAGE发布映射或生成快照。
- 只有产品对上一轮完整结论包作无保留确认时，才按包内预览写入；确认使该拟定结论成为明确产品决议。检查通过和 `active` 均不能替代确认。
- “确认 / 同意 / 按此结论执行 / 按建议做 / 确认落盘”可视为确认；“继续 / 可以继续”只表示工作流继续，不视为产品确认。
- 用户附带修改意见时不得边改边落盘；先重发完整修订结论包，再等确认。
- `通过`：范围级与全部范围行均为 `approved`、产品确认项为 0、阻塞决策为 0、未决决策全部 `closed` 时，范围才可记为完整批准，随后可进入 ⑨。
- `不进入本期`：产品确认项为 0、范围为空、未决决策全部 `closed` 时记为 `approved`；无需 ⑨，可由 ⑩ 视为已闭合版本。
- `附条件通过` / `退回补充`：即使产品确认了该阶段结论，也不发布PAGE快照；按后续动作返回②③④⑤、Q-S、⑥、Q-P后重新评审。
- `通过`：从根 `pages_prd/{终端}/PAGE-*.md` 按PAGE发布映射生成版本快照。目标目录使用完整页面路由，文件名保持PAGE ID；快照加注所属版本与本版Feature/AC范围。禁止复制 `_shell`；非首版可保留未变化的已发布基线行为，禁止带入未批准的本版变化。
- 用户只关闭部分问题时，只更新对应行和计数，不顺带批准整个范围。
- 用户决议与生命周期冲突时不写冲突值，说明缺口并委派 `/lny-prd-feature`。

### 6.3 禁止写入

- 不创建缺失的版本目录；版本目录属于 ①/⑩。目录存在时，本技能可在确认轮创建 `delivery_scope.md`。
- 不修改 `iteration_notes.md`、三类 `*_changes.md`、`eval_signals.md` 或根规范变更记录。
- 不直接修改根 Feature 其它正文。结论包含 Feature 评审状态时，在确认轮按 `/lny-prd-feature` 规则同轮同步该字段。

## 7. 与 check 的分界

`review` 判断范围与方案是否合理并记录确认结论；`check` 只验证规格事实、实现证据和是否具备发起评审的条件。

- 缺少 `delivery_scope.md`：在⑧确认前是正常状态，不属于⑦缺陷；⑦只判断是否建议发起⑧。
- 已有范围仍为 `reviewing/blocked` 或存在 open 决策：说明上次评审未终结，由⑧继续修订循环。
- 生命周期、枚举、计数或引用不一致：`check` 报客观错误，按事实所有者委派。
- 是否通过、删减或延期：由 `/lny-prd-review` 形成拟定结论，产品确认后生效。

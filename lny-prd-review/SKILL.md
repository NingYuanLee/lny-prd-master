## 与总控的关系

本步为 **⑧ `/lny-prd-review`**。进入前须有本轮有效的⑦/Q-S与Q-P；默认主链在Q-P通过后询问产品是否进入本步，用户已明确要求评审则直接进入。⑧基于目标版本的证据层、当前规格、当前原型和两道门禁做产品判断，并执行PAGE版本范围原子性门禁。调整、附条件或退回会按影响范围返回②③④→⑤→Q-S→⑥→Q-P，再回本步。只有最终“通过”经产品确认后，才创建或更新 `delivery_scope.md`、按真实路由发布批准PAGE快照，并按需同步Feature评审状态。

## 两种模式

### 1. 拟定结论模式（默认，只读）

读取用户指定的 FEATURE、版本范围或完整 PRD，区分事实、推断与待确认信息，从用户价值、目标、范围、方案、验收、风险等维度形成**唯一、明确、可执行的拟定结论**。不得把选择题留给产品；材料足以判断时必须选定结论档位、范围取舍和确认后的状态变化。首次输出不修改项目文件，结论标记“待产品确认”。

### 2. 结论确认与记录模式

满足以下条件时进入：

1. 上一轮由本技能给出了同一对象、同一版本的完整拟定结论包；
2. 用户直接回复“确认 / 同意 / 按此结论执行 / 按建议做 / 确认落盘”等无保留确认；
3. 结论涉及版本范围时，目标 `versions/{v}/` 已存在；`delivery_scope.md` 可不存在，由确认轮创建。

确认回复等价于产品明确采纳上一轮完整结论，用户无需逐项复述。若用户补充事实、调整范围、修改条件或质疑结论，进入评审修订循环：先判断这些变化是否改变依据与风险，说明采纳或不采纳的理由，再输出一份自足的修订结论包等待确认。不得机械迎合，也不得要求产品自己重写整份结论。`继续`、`可以继续`等通用流程口令不等于确认产品结论。

范围结论由本技能在确认轮整块创建或更新 `delivery_scope.md`。最终“通过”时，同轮从根 `pages_prd/` 发布批准PAGE快照到版本目录；`附条件通过`、`退回补充`和`不进入本期`不发布页面。结论包含Feature评审状态时，同轮Read `/lny-prd-feature` 同步。不得复制根 `_shell`，不得创建版本目录、修改原型、SP或流水。

## 工作版本与对象

- 用户指定 `vX.Y.Z` 且目录存在时使用该版本；否则使用 `versions/` 最大 semver。
- **首版**（`versions/` 中最早semver）：无前版基线与变更台账时，以用户当前取舍和根 `main_spec` / `feature_spec` / `feature/` / `ui/` / `api/` / `pages_prd/` 的当前完整规格组装候选；不得仅因 `active` 自动批准，但须检查同页全部待发布active Feature的范围原子性。
- **非首版**：当前版本三类 `*_changes.md` 回答“本版改什么”，其中 `feature_changes.md` 为候选主入口，`ui_changes.md` / `api_changes.md` 用于反查受影响Feature；根目录规格回答“修改后完整事实”，上一版本 `delivery_scope.md` 与批准PAGE快照回答“已发布基线”。三层均须读取，禁止只看change文档或只看根目录。
- 未指定对象时优先读取目标版本已有 `delivery_scope.md`；不存在时按上述版本口径和用户明确目标组装候选。不得把全部active Feature自动纳入，但必须主动给出候选取舍，不能要求产品先整理清单。
- 用户指定 `FEATURE-*` 时只评审该对象及其直接 STORY、AC、PAGE、API/EXT 证据，除非跨 Feature 依赖会改变结论。
- 旧版本默认只读；只有用户明确要求纠正该版本历史决议并确认事实时才可记录。

## 执行步骤

1. Read [`reference.md`](reference.md) 与框架排除。若没有同一对象、版本和当前内容的有效Q-S/Q-P，先自动补齐规格/原型链与两道门禁；若会写入，再Read产物路径契约。
2. 先判首版/非首版并建立证据层。读取根 `main_spec.md` 的用户/故事、产品目标、成功怎么算、明确不做，以及评审对象对应的Feature、UI/API、单页PRD；非首版另读当前版本三类变更台账、上一版本范围与批准PAGE快照；已有目标版本 `delivery_scope.md` 时也读取。按reference组装候选范围。
3. 区分 ⑦ 的客观问题、产品判断依据与仍缺的事实，再做判断；不得为缺失的用户研究、收益、优先级、成本或批准结论编造事实。
4. 在拟定“通过”前执行PAGE版本范围原子性门禁：同一PAGE的本版受影响Feature不得部分纳入、部分不纳入。冲突时必须选定“调整范围一并纳入”或“返回受影响②③④拆解”，不得生成可确认的通过结论。随后输出完整拟定结论包；本轮不落盘。
5. 用户提出调整时重发完整修订结论。产品确认调整/附条件/退回后，按后续动作从最早责任步骤返修并自动回到本步；产品确认最终“通过”时，创建或更新 `delivery_scope.md`，发布批准PAGE路由快照，按需同步Feature评审状态，最后报告实际发布范围。

确认后下一步必须按结论明确给出：`通过` 且有交付范围 → ⑨ `/lny-prd-sp`；`不进入本期` 且范围为空 → 可考虑 ⑩ `/lny-prd-iter`；`附条件通过` / `退回补充` → 先完成结论中的动作并重新进入⑦/⑧，不得建议⑨或⑩。

## 结论与边界

- 拟定结论只用“通过 / 附条件通过 / 退回补充 / 不进入本期”，并标记“待产品确认”；不得只罗列利弊而拒绝下结论。
- 产品确认后，上一轮完整结论即成为明确产品决议；`approved`、范围成员变化和 `closed` 可按该结论记录。
- 根 `feature_spec.md` / `feature/` 的评审状态仍由 `/lny-prd-feature` 维护；本技能在确认轮同轮调用其规则同步，无需产品二次确认。
- 文档一致性与引用闭环属于⑦/Q-S，原型符合规格属于⑦/Q-P；本技能引用两者，不复制检查表。
- 创建新版本目录属于 ⑩ `/lny-prd-iter`；创建和维护 `delivery_scope.md` 只属于本技能。

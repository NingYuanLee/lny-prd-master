# 迭代台账与落盘模板

执行 `/lny-prd-iter` 时 Read 本节后落盘。SKILL 只定边界与步骤。

## 输入变量

```yaml
操作模式: new-version  # new-version / update-scope
版本号: v1.1.0
版本名称:    # 可选；给人看的短名。无则用迭代内容简述
新增页面: [PAGE-MP-004]
修改页面: [PAGE-MP-001]
废弃页面: [PAGE-MP-003]
新增接口: [API-MP-010]
修改接口: [API-MP-002]
废弃接口: [API-MP-003]
新增功能: [FEATURE-010]
修改功能: [FEATURE-003]
废弃功能: [FEATURE-001]
本期开发功能: [FEATURE-010, FEATURE-003]  # 必须显式给出；可包含本期未修改但要交付的既有 Feature
本期下线功能: [FEATURE-001]  # 可省略；新版本默认取废弃功能，update-scope 时须显式给出
范围评审状态: pending  # pending / reviewing / approved / blocked；无明确批准不得写 approved
产品确认项: 1  # 非负整数
未决决策:
  - 决策编号: DECISION-001
    状态: open
    问题: {待产品确认的问题}
    影响对象: FEATURE-010
变更形态:  # 可省略；按条覆盖。默认：新增→新建，修改→修改，废弃→废弃删除；用户明示可复用→复制扩展
存量数据影响: 无  # 可省略，默认无。取值：无 / 需迁移 / 需备份或回滚预案。禁止 DDL
```

`update-scope` 只需要版本号、本期开发功能、本期下线功能、范围评审状态、产品确认项与未决决策；禁止附带或改写页面/API/Feature 台账。用户用自然语言明确同样事实时可等价解析。新版本模式中，`废弃功能` 自动进入 `本期下线功能`；两者同时给出时必须一致。

功能编号用 `FEATURE-{三位序号}`；历史 `FEATURE-MP-001` 可出现在输入中。列表项可省略。

用户可给 YAML 或自然语言。一句意图可拆多行（例：「首页改版并加登录接口」→ 修改 PAGE + 新增 API）。ID 已知则填入；未知则 `ID` 写 `待确认`、`摘要` 写原意、`委派步` 仍标明。关键词「下线/废弃/删除/不再使用」且对象为页面/接口/功能 → 操作列 **废弃**（不删文件）；废弃 Feature 同时进入 `delivery_scope.md` 的 `本期下线` 行。禁止模糊的 `UI变更: 描述文字`。`本期开发功能` 未给出时不得从全部 active Feature 或其他变更台账自动推断，`delivery_scope.md` 保持待确认阻塞壳。

## 统一台账表

三类 `*_changes.md` 同表（无变更时保留表头，正文写 **无**）：

```markdown
# {UI|API|Feature} 变更台账 - {版本号}

| ID | 操作 | 变更形态 | 存量数据影响 | 摘要 | 委派步 | pages_prd目标路径 | 状态 |
|----|------|----------|--------------|------|--------|-------------------|------|
| PAGE-MP-004 | 新增 | 新建 | 无 | {一句话} | ② | versions/{v}/pages_prd/pages/index/PAGE-MP-004.md | 待② |
| PAGE-MP-001 | 修改 | 修改 | 无 | {一句话} | ② | versions/{v}/pages_prd/pages/index/PAGE-MP-001.md | 待② |
| PAGE-MP-003 | 废弃 | 废弃删除 | 需备份或回滚预案 | {一句话} | ② | 无需单页 PRD | 待② |
| API-MP-010 | 新增 | 复制扩展 | 无 | {一句话} | ③ | — | 待③ |
| FEATURE-010 | 修改 | 修改 | 需迁移 | {一句话} | ④ | — | 待④ |
```

| 列 | 取值 |
|----|------|
| 操作 | `新增` / `修改` / `废弃` |
| 变更形态 | `新建` / `复制扩展` / `修改` / `废弃删除`（必填；复制扩展 = 以既有为底少改；默认随操作；用户明示可复用时用 `复制扩展`） |
| 存量数据影响 | `无` / `需迁移` / `需备份或回滚预案`（必填；禁止 DDL/表名） |
| 状态 | 单值：`待②` / `待③` / `待④` / `待⑤` / `已完成`（本步只初始化） |
| pages_prd目标路径 | 仅新增/修改页面填写（规则见 `lny-prd-page`）；废弃页面填 `无需单页 PRD` 或 `—`；api/feature 填 `—` |

同一页面新增或修改：一行覆盖 ② 与 ⑤；`pages_prd目标路径` 必填；初始状态只写 `待②`。② 成功后把该行改为 `待⑤`，⑤ 成功后改为 `已完成`。废弃页面由 ② 成功后直接转 `已完成`。禁止复合状态 `待②/待⑤`。

## `eval_signals.md`

必建。从三类台账汇总，不计 SP，禁止长文。

```markdown
# 迭代估点信号 - {版本号}

> 阶段 1 只采信号、不计标准工时点。明细以三类 `*_changes.md` 为准；本文件为汇总。

## 1. 变更形态统计

| 变更形态 | UI | API | Feature | 合计 |
|----------|----|-----|---------|------|
| 新建 | n | n | n | n |
| 复制扩展 | n | n | n | n |
| 修改 | n | n | n | n |
| 废弃删除 | n | n | n | n |

## 2. 存量数据影响统计

| 存量数据影响 | UI | API | Feature | 合计 |
|--------------|----|-----|---------|------|
| 无 | n | n | n | n |
| 需迁移 | n | n | n | n |
| 需备份或回滚预案 | n | n | n | n |

## 3. 需关注条目（存量 ≠ 无）

| ID | 台账 | 变更形态 | 存量数据影响 | 摘要 |
|----|------|----------|--------------|------|
| {FEATURE-010} | feature | 修改 | 需迁移 | {一句话} |
| {无则一行写无} | — | — | — | 无 |
```

## `iteration_notes.md` 开篇

```markdown
# 迭代摘要 - {版本号}

## 版本名称
{版本名称；无则用迭代内容简述}

## 版本目标
{迭代内容简述}

## 变更统计
- 页面：新增 n / 修改 n / 废弃 n
- 接口：新增 n / 修改 n / 废弃 n
- 功能：新增 n / 修改 n / 废弃 n
- 估点信号：见同目录 `eval_signals.md`（不计点）

## 委派顺序
1. `/lny-prd-ui`（②）— {待办 PAGE 摘要}
2. `/lny-prd-api`（③）— {待办 API 摘要}
3. `/lny-prd-feature`（④）— {待办 FEATURE 摘要}
4. `/lny-prd-page`（⑤）— {待办 pages_prd 路径列表}
5. `/lny-prd-prototype`（⑥）— 有新增/修改页面时必做；仅 API/Feature 变更时可选
6. `/lny-prd-check`（⑦）— 须用户明确要求检查，不随「继续」自动跑
7. `/lny-prd-sp`（⑨）— 台账与规格就绪后按本版本估点（可选）
```

文末流水过滤见 `lny-prd-master/SKILL.md` §1.1.1 / §1.1.2。⑧ 只写开篇；②③④⑤ 按序追加；⑥⑦⑨ 不维护流水。

## `delivery_scope.md`

必建，用于声明本期实际开发范围与产品评审门禁。它不复制 Feature 正文，也不保存云效工作项 ID、负责人或研发状态。

```markdown
# 交付范围 - {版本号}

## 1. 范围状态

> **产品经理填写说明**
> - `评审状态` 只填一个值：尚未发起评审填 `pending`；正在评审填 `reviewing`；存在阻塞、暂不能确认范围填 `blocked`；本期范围已明确且不存在未关闭问题时填 `approved`。
> - `产品确认项` 填仍未关闭且影响本期范围确认的问题数量。每关闭一项同步递减，全部关闭后改为 `0`。
> - 推荐流转：`pending` -> `reviewing` -> `approved`；评审中发现阻塞时改为 `blocked`，解除阻塞后回到 `reviewing`，重新确认后再改为 `approved`。

| 属性 | 内容 |
|------|------|
| 版本号 | {版本号} |
| 评审状态 | pending |
| 产品确认项 | {非负整数} |

## 2. Feature 范围

> **产品经理填写说明**
> - `Feature` 填根 `feature_spec.md` 中已登记的 `FEATURE-###`；尚未确定时保留阻塞壳，不能从全部 `active` Feature 自动推断。
> - `纳入方式`：确定本期实现时填 `本期开发`；本期明确废弃并需关闭外部研发工作项时填 `本期下线`；尚未确定时填 `待确认`；其余 Feature 不保留在本表中。
> - 生命周期必须匹配：`本期开发` 对应 Feature `状态=active`，`本期下线` 对应 `状态=deprecated`；废弃只改状态并保留历史明细文件。
> - 行级 `评审状态` 与范围级使用同一组状态，但表示该 Feature 的开发或下线结论是否已经确认；只有已确认的本期 Feature 才改为 `approved`。
> - `阻塞决策` 填下方仍为 `open` 且影响该 Feature 的决策数量；相关决策关闭后同步递减，全部关闭后改为 `0`。

| Feature | 纳入方式 | 评审状态 | 阻塞决策 |
|---------|----------|----------|----------|
| FEATURE-010 | 本期开发 | pending | {非负整数} |
| FEATURE-001 | 本期下线 | pending | {非负整数} |

## 3. 未决决策

> **产品经理填写说明**
> - 每个待确认问题单独一行：未形成结论填 `open`，形成明确结论并已同步相关 PRD 后改为 `closed`。
> - `影响对象` 填受影响的 `FEATURE-###`；影响多个 Feature 时用逗号分隔。没有未决问题时仅保留 `| 无 | closed | 无 | 无 |`。
> - 所有决策均为 `closed` 后，才可把上方对应的 `阻塞决策` 归零；其他门禁也满足后，再将评审状态改为 `approved`。

| 决策编号 | 状态 | 问题 | 影响对象 |
|----------|------|------|----------|
| DECISION-001 | open | {待确认问题} | FEATURE-010 |
```

只有范围级与 Feature 行均为 `approved`、确认/阻塞数均为 0、未决决策全部 `closed` 时，才具备外部研发台账导出条件。`本期开发` 导出更新计划；`本期下线` 还要求最近更早版本保留已审阅的 `yunxiao-plan.json`，关闭计划按该快照中实际存在的子任务生成，不能用当前 Feature 引用猜测。没有用户明确批准时保持 `pending`，不得把 Feature 的生命周期状态替代产品批准。若当前没有未决决策，将示例决策行替换为 `| 无 | closed | 无 | 无 |`。

## 版本号校验

1. 格式 `v{主}.{次}.{修订}`
2. 须 **>** `versions/` 下当前最新（与变更记录冲突时以 `versions/` 为准并说明）
3. 合理递增：v1.2.3 → v1.2.4 / v1.3.0 / v2.0.0；跳跃允许但警告；递减报错

# 立项模板

立项 YAML 与 `main_spec.md` 骨架。立项时 Read 本节落盘；**不在项目内落地 `.templates/`**。

## 立项 YAML

```yaml
项目名称:
产品定位:
需求故事:
  - 类型: 用户价值   # 用户价值 / 运营 / 合规 / 迁移 / 技术使能
    角色: {用户、利益相关方或责任角色}
    背景: {角色画像或需求背景}
    故事: {作为...我需要...以便...}
产品目标:
终端范围: [小程序, App, 管理后台]
竞品参考: (可选)
专业术语介绍: (可选)
框架排除 profile: lny-default   # 默认沿用；确认摘要必须列出 exclusions「确认摘要必列类别」；看不见清单不得请用户确认；改则 none 或自定义
框架内置排除: []   # 在默认排除之上的本项目追加项
成功怎么算:    # 可选，1～3 句
明确不做: []   # 可选
```

### 换栈对照（`none`）

非作者栈、或要把登录/支付等当业务需求展开时，立项 YAML 用 `none`。确认摘要须写「无默认排除，仅遵守本项目追加项」。

```yaml
项目名称: {项目名称}
产品定位: {一句话}
需求故事:
  - 类型: 用户价值
    角色: {用户、利益相关方或责任角色}
    背景: {角色画像或需求背景}
    故事: {作为...我需要...以便...}
产品目标: {要达成什么}
终端范围: [小程序, 管理后台]
框架排除 profile: none
框架内置排除: []   # 仅本项目追加；默认为空
成功怎么算:    # 可选
明确不做: []   # 可选
```

需要自定义排除表时：把 `framework-exclusions.md` 拷到 PRD 项目根后改，或把类别写入 `框架内置排除`。

| 版本 | 日期 | 变更内容 | 作者 |
|------|------|----------|------|
| v1.0.0 | {创建日期} | 初始版本 | PM |

## 1. 项目概述

{产品定位与愿景}

### 1.2 需求故事

| 故事编号 | 故事类型 | 角色 / 利益相关方 | 画像 / 背景 | 需求故事 |
|----------|----------|-------------------|-------------|----------|

> STORY 只维护需求来源事实，不手工登记 FEATURE。`feature/FEATURE-*.md` 的「关联 STORY」是 STORY↔FEATURE 的唯一事实源；Story 覆盖情况由扫描 Feature 明细反查。立项后尚未拆出 Feature 的 Story 视为待拆解，不得用「框架承接」伪装已承接。

### 1.3 竞品分析
{竞品分析内容}

### 1.4 成功怎么算（可选）
{1～3 句；未填写则写「未填写」}

### 1.5 明确不做（可选）
- {未声明则写「未声明」}

## 2. 通用规范与阅读指南

### 2.1 编号规则与追溯（速查）

| 类型 | 编号规则 | 说明 |
|------|----------|------|
| 终端 | MP 小程序 / APP / H5 / PC / AD 管理后台 | 终端清单见 §4 |
| 页面 | `PAGE-{终端类型编码}-{三位序号}` | 如 `PAGE-MP-001` |
| 接口 | `API-{终端类型编码}-{三位序号}` | 如 `API-MP-001` |
| 第三方接口 | `EXT-{三位序号}` | 如 `EXT-001` |
| 组件 | `COMP-{三位序号}` | 如 `COMP-001` |
| 功能 | `FEATURE-{三位序号}` | 如 `FEATURE-001` |
| 业务模块 | `MODULE-{三位序号}` | 领域定义在 `feature_spec.md`；模块改名时编号不变 |
| 需求故事 | `STORY-{三位序号}` | 与 FEATURE 可为 N:M；映射只在 FEATURE 明细维护 |

**四驱动追溯模型**：规格承载全部事实；`STORY → FEATURE → AC（验收标准）→ PAGE / API / EXT` 是价值与验收主线，`FEATURE → MODULE` 是领域归属。任何正式 Feature 都须有 Story、唯一 Module 与可验证 AC；断链即规格不完整。路由/路径约定见 `ui_manifest.md` §3。

### 2.2 文档地图（入口清单）

| 文档 | 用途 |
|------|------|
| 本文件 `main_spec.md` | 产品全貌、终端（§4）、三大索引（§5/§6/§7） |
| `ui_manifest.md` + `ui/` | 页面/组件清单与详述（布局、状态、组件） |
| `api_spec.md` + `api/` | 接口需求（业务语义，非技术契约） |
| `feature_spec.md` + `feature/` | 领域模块边界与功能规格（目标、规则、AC、时序/流程图） |
| `versions/{v}/delivery_scope.md` | 本期评审确认的开发/下线范围（feature_spec 里的 active Feature 未必本期都开发） |
| `versions/{v}/*_changes.md` | 迭代版本（非 v1.0.0）相对上一版的变更清单（新增/修改/废弃 + 存量数据影响） |
| `versions/{v}/pages_prd/` | 单页 PRD（逐页数据来源、跳转、API 交互） |
| `prototypes/` | 静态原型（仅视觉参考，见 §2.6） |

### 2.3 开发侧阅读顺序（按依赖，非硬性分工）

- **先总后分**：`main_spec`（§1 概述 / §4 终端）→ 相应索引（`ui_manifest` / `api_spec` / `feature_spec`）→ 明细（`ui/` / `api/` / `feature/`）→ `pages_prd` → `prototypes/`。
- **按功能追踪**：从 `feature/` 的 AC、规则、时序图定位涉及的 `PAGE-*` 与 `API-*`，再到对应 `ui/PAGE-*` 与 `pages_prd` 看该页。
- **FE/BE 只是主入口建议，不是分工边界**：FE 多从 `ui/` + `pages_prd` 入手，BE 多从 `api/` + `feature/` 入手；但 **AD 管理后台页通常由 BE/全栈承担**，此时 BE 同样要读 `ui/PAGE-AD-*` 与 `pages_prd` 的 AD 页。跨端团队按实际归属补齐，勿因「FE/BE」字样漏读。

### 2.4 技术选型决策点（开发侧自定）

本套 PRD 只写「产品要什么」，不写「怎么实现」。以下由开发侧在实现阶段自行决定：框架/语言、数据库与 DDL、API 的 path/HTTP 方法/JSON 字段/响应 code、缓存与鉴权实现、路由落地。

### 2.5 验收标准与测试约定

Feature 的 AC 是自然语言验收标准，不是可执行测试。开发侧需把每条 AC 翻译为测试用例，并保留 AC 编号 ↔ 测试的映射（如 `AC-3 → T-FEATURE-001-3`），便于回归对照。

### 2.6 原型定位

`prototypes/` 是静态展示品，仅作视觉/交互参考，不是可上线前端工程；没有路由、状态管理、接口联调。开发侧应另起工程实现，不得在原型 HTML 上继续开发。

### 2.7 非需求文件（开发侧可忽略）

`versions/{v}/` 下的 `sp_report.md`（标准工时点）、`eval_signals.md`（迭代估点信号）、`iteration_notes.md`（过程流水）是产品估点/过程记录，编码实现无需阅读。

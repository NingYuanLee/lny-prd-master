## 规范参考

- 编号体系：`main_spec.md` → **§2.1 编号规则说明**
- UI 事实源：`ui_manifest.md` 索引 + `ui/PAGE-*.md` / `ui/COMP-*.md`（旧版兼容 `ui_manifest` 内嵌全文）
- 接口需求：`api_spec.md` **§4** 索引 + `api/API-*.md`；第三方：`api_spec` **§2** + `api/EXT-*.md`
- Feature：`feature_spec.md` 索引 + `feature/FEATURE-*.md`
- 单页 PRD：`versions/{版本号}/pages_prd/**/*.md`（含 `pages/`、`subpackages/`、`views/`、`_shell/` 等嵌套；**不含**仅目录占位）
- 原型：根目录 `prototypes/{终端}/**/*.html`；若存在镜像则另核 `versions/{版本号}/prototypes/{终端}/**/*.html`

- 必须已执行 `/lny-prd-master` 初始化项目（至少存在 `main_spec.md`）

## 工作版本

无单独输入变量。工作版本按 `lny-prd-master` **§1.1「当前工作版本号」**：用户消息里**显式给出**且目录已存在的 `vX.Y.Z` 优先，否则取 `versions/` 下 semver **最大**；报告抬头须写明实际使用版本。

## 优先级评价标准

| 等级 | 图标 | 定义 |
|------|------|------|
| 高 | 🔴 | **阻塞性问题**：导致后续步骤无法执行、规格间存在矛盾、数据完整性与可追溯性受损。须优先修复。 |
| 中 | 🟠 | **质量问题**：影响最终交付质量或团队协作效率，但不阻塞流程推进。建议在进入下一步前修复。 |
| 低 | 🟢 | **优化建议**：格式规范、可读性提升、锦上添花的改进项。可择机处理，不阻塞。 |

> 报告输出时在分节标题与条目前置对应色点：`🔴 高优先级` / `🟠 中优先级` / `🟢 低优先级`；表格「优先级」列可写 `🔴` / `🟠` / `🟢`（可附文字高/中/低）。

## 状态口径（FEATURE / API，供 1.4 与 3.x）

> **这是什么**：估点与「可评估链」只应对 **仍有效** 的功能/接口计数。feature 技能用 `draft` / `active` / `deprecated`；api 未必有同级枚举。本步统一如下，避免「active」含义不清。

| 对象 | 如何判定「纳入可估 / 信号采集」 | 不纳入时 |
|------|-------------------------------|----------|
| **FEATURE** | 索引或明细 **状态** = `active`；**未写状态** → 视为 `active` | `draft`：不阻塞可估链，但 FE⑥/BE⑦ 可不计或单列「草稿未估」；`deprecated`：不计入可估与 BE⑦ |
| **API** | 未标废弃/deprecated → 视为纳入（「active」）；明细或索引明确 `deprecated` / `废弃` → 不纳入 BE②～⑤ | 仅写「草稿」且项目约定草稿不计分时，标 BE 信号时注明「草稿未计入」 |
| **PAGE / EXT** | 无废弃标记则纳入对应 FE/BE 维；明确废弃则排除 | 报告中注明排除编号 |

## 一、文档性检查

对根规格文档及明细目录的规范性、完整性、一致性做只读检查，不涉及原型实现。

> **检查顺序（须按下列小节依次执行）**：先确认 **结构壳齐全** → **编号与索引一致性**（格式/数量/唯一/清单↔文件夹）→ **内容格式** → **文档内交叉引用闭环**（含产品可评估链举证）→ **版本/台账** → 其它。  
> 编号事实源：`main_spec` **§2.1**（`STORY` / `FEATURE` / `PAGE` / `COMP` / `API` / `EXT`）。

### 1.1 结构完整性类

> **纯文档级、不读正文**：只确认文件/目录是否存在、是否落在约定位置。**禁止**打开正文核对章节标题或字段；章节与内容细项归 1.2～1.4。四份根规范须逐份过，不得只查 UI。

| 检查项 | 规则 | 不通过建议 | 优先级 |
|--------|------|------------|--------|
| 根规范文件存在 | 项目根存在 `main_spec.md`、`ui_manifest.md`、`api_spec.md`、`feature_spec.md`（缺哪份报哪份） | 缺则走 `/lny-prd-master` 或对应子技能补建 | 高 |
| 明细目录存在 | 存在 `ui/`、`api/`、`feature/`（可空） | 创建空目录或走对应步初始化 | 高 |
| 版本目录存在 | 工作版本对应 `versions/{v}/` 存在；有台账/单页时对应子路径目录存在即可（不读文件内容） | `/lny-prd-iter` / `/lny-prd-page` 补目录 | 中 |
| `ui/` 落点归属 | 凡 `PAGE-*.md`/`COMP-*.md` 须在 `ui/` 下，不得散落根目录或其它目录（只看路径，不读文件） | `/lny-prd-ui` 迁移 | 高 |
| `api/` 落点归属 | 凡 `API-*.md`/`EXT-*.md` 须在 `api/` 下（只看路径） | `/lny-prd-api` 迁移 | 高 |
| `feature/` 落点归属 | 凡 `FEATURE-*.md` 须在 `feature/` 下（只看路径） | `/lny-prd-feature` 迁移 | 高 |
| `pages_prd` 落点归属 | 单页 PRD 文件须在 `versions/{v}/pages_prd/` 树下（允许嵌套子目录；只看路径） | `/lny-prd-page` 迁移 | 中 |
| `prototypes` 落点归属 | 页原型 `PAGE-*.html` 须在 `prototypes/{终端}/` 下且 `{终端}` 与文件名终端编码一致（只看路径；有无文件见 1.6） | `/lny-prd-prototype` 迁移 | 中 |

### 1.2 编号与索引一致性类

> **只查清单登记册**：编号规则（§2.1）+ 编号数量（清单行数 = 对应明细文件数）+ 清单内无重复 + 清单 ↔ 文件夹双向一致且唯一。  
> **不查**文档正文里的交叉引用——归 **§1.4**。  
> **索引类优先级统一为高**（FEATURE / PAGE / COMP / API / EXT 同类断裂同等阻塞）。

| 检查项 | 规则 | 不通过建议 | 优先级 |
|--------|------|------------|--------|
| STORY 编号与数量 | `STORY-{三位序号}`；`main_spec` §1.2 清单内格式正确、**无重复**；记清单条数（故事无独立明细目录，不要求文件夹对账） | `/lny-prd-master` 修正格式/去重 | 高 |
| FEATURE 编号与索引 | `FEATURE-{三位序号}`；`feature_spec` 清单：格式正确、**无重复**、条数 = `feature/FEATURE-*.md` 数；清单 ↔ 文件夹 **双向一致且唯一** | `/lny-prd-feature` 修正/去重/补文件或索引行 | 高 |
| PAGE 编号与索引 | `PAGE-{终端}-{三位序号}`（终端 ∈ MP/APP/H5/PC/AD）；`ui_manifest` 清单：格式正确、无重复、条数 = `ui/PAGE-*.md` 数；双向一致且唯一 | `/lny-prd-ui` 修正/去重/补文件或索引行 | 高 |
| COMP 编号与索引 | `COMP-{三位序号}`；`ui_manifest` 清单：格式正确、无重复、条数 = `ui/COMP-*.md` 数；双向一致且唯一 | `/lny-prd-ui` 修正/去重/补文件或索引行 | 高 |
| API 编号与索引 | `API-{终端}-{三位序号}`；`api_spec` §4 清单：格式正确、无重复、条数 = `api/API-*.md` 数；双向一致且唯一 | `/lny-prd-api` 修正/去重/补文件或索引行 | 高 |
| EXT 编号与索引 | `EXT-{三位序号}`；`api_spec` §2 清单：格式正确、无重复、条数 = `api/EXT-*.md` 数（清单为「无」时文件夹应无 EXT 明细）；双向一致且唯一 | `/lny-prd-api` 修正/去重/补文件或索引行 | 高 |
| `main_spec` §5 统计对账 | `main_spec` §5 有效页面数 / 有效跨页面组件数（若项目维护）与 `ui_manifest` §3 / §4（及 `ui/` 实文件）一致 | `/lny-prd-ui` 更新 §5 统计 | 中 |
| 页面模块编号（条件启用） | **仅当** `ui_manifest` 或 `ui/PAGE-*` 出现「模块编号 / 区域编号」列，或正文使用 `{PAGE-*}-{区域缩写}` 形式时才检查：格式为 `{页面编号}-{区域缩写}`、同清单无重复。**未出现则跳过、不报** | 修改区域缩写或对齐页面编号；建议统一在 PAGE §2 分区标题旁标注 | 低 |

### 1.3 内容格式规范类

> 只查 **可读性与 Markdown/编码形态**，不查业务语义、实现越界或主文档↔API 对齐（该类历史项已废弃）。

| 检查项 | 规则 | 不通过建议 | 优先级 |
|--------|------|------------|--------|
| 编码与乱码 | `.md` 等规格正文须为 **UTF-8（无 BOM）**；不得出现典型乱码（大量 `�`、GBK 误读花码、无意义控制字符）；大面积不可读可升 🔴 | 以 UTF-8 无 BOM 重存并修复乱码段 | 中 |
| Markdown 围栏闭合 | \`\`\` / `~~~` 须成对；不得因未闭合导致后续正文被吞进代码块 | 补闭合围栏或拆开误并段落 | 中 |
| Markdown 表格格式 | 含表头的表须有分隔行（`\| --- \|`）；同表行列 `|` 数量明显不一致须报 | 补分隔行或对齐列数 | 中 |
| 标题层级连贯 | 同文件内标题层级不得明显跳级（如 `#` 后直接 `####`）；空标题（仅有 `#` 无文字）须报 | 调整层级或补全标题文字 | 低 |
| 链接与括号闭合 | Markdown 链接 `[]()`、图片 `![]()` 括号成对；明显残缺链接（有 `]` 无 `(` 等）须报 | 补全或删除残缺标记 | 低 |
| 空壳结构 | 连续多个标题下完全无正文/表/列表，或整节仅空白占位，影响阅读时须报 | 补正文或删空壳标题 | 低 |
| 图示围栏（若有） | Mermaid / 时序图等须落在已闭合代码围栏内，且围栏语言标记与内容类型大致匹配（如 `mermaid`） | 补围栏或修正语言标记 | 低 |

### 1.4 引用闭环类（含产品可评估链举证）

> **文档内交叉引用**（须读关联字段/正文引用）：编号登记册本身的格式/数量/唯一/清单↔文件夹已在 §1.2 验过。  
> **产品可评估链**（STORY→FEATURE→AC→PAGE→API）的**问题条目在此开列**；§3.1 **只虚引用本类结论**判可估，**不**再重复计条。

| 检查项 | 规则 | 不通过建议 | 优先级 |
|--------|------|------------|--------|
| 故事↔功能 | `main_spec` §1.2 每条 `STORY-*` 关联列为有效 `FEATURE-*` 或显式「框架承接」；被引用 FEATURE 须在 `feature_spec` 存在 | `/lny-prd-master` / `/lny-prd-feature` 补关联或改编号 | 高 |
| FEATURE↔AC | 每个 **active** FEATURE（见「状态口径」）有可验证 AC 表；有数据依赖的 AC 挂 `API-*` / `EXT-*` 或显式「无」 | `/lny-prd-feature` 补 AC / 关联接口 | 高 |
| Feature↔页面/接口 | 每个 FEATURE 关联页面、关联接口非空或显式「无」；页面 ∈ `ui_manifest`；接口 ∈ `api_spec` **§4（API）** 或 **§2（EXT）**，无孤儿引用 | `/lny-prd-feature` 修复引用或补齐页面/接口 | 高 |
| 非静态 PAGE↔API | 非静态页须关联至少一 `API-*` 或正文标明静态/无数据；静态页须标明 | `/lny-prd-ui` / `/lny-prd-api` 补关联或标静态 | 中 |
| API 元数据完备 | 纳入口径的 API 明细含 **服务对象**、**数据操作形态**、**API是否涉及第三方联动**、**响应形态**；联动为「是」须挂 `EXT-*` | `/lny-prd-api` 补字段或 EXT | 中 |
| 接口编号存在性 | 规格 / `pages_prd/**/*.md` 等正文中引用的 `API-*` 须在 `api_spec` §4；`EXT-*` 须在 §2 | 补充或修正引用 | 高 |
| 页面跳转闭环 | **出边**：跳转目标 `PAGE-*` 须在 `ui_manifest` / `ui/` 存在。**回边**：仅当规格或单页 PRD **写明**须可返回/双向时，才检查反向入口；未写明则不要求「双向可达」 | 补充缺失页面或修正跳转；需回边时补返回入口 | 中 |
| 接口覆盖率 | 每个非静态页面至少关联一个接口（静态页须标明）；与「非静态 PAGE↔API」同源，择一详报即可免双计 | 补充接口或标记静态 | 低 |
| 局部自定义 UI 组件规格 | 每个 `ui/COMP-*.md` 含设计前提与 UI 状态矩阵；`ui/PAGE-*` 未重复 COMP 内状态详述 | `/lny-prd-ui` 补矩阵或删 PAGE 重复描述 | 中 |
| 局部组件聚合与拆页 | 视觉相邻且同一状态机的区块未错误拆成多个 COMP；单页 ≥3 独立状态机/数据域时 `ui/PAGE-*` 有拆分说明 | `/lny-prd-ui` 合并 COMP 或补拆页说明 | 中 |

## 二、功能性验收

以用户视角对照规格文档（② `ui/`、③ `api/`、④ `feature/`、⑤ `pages_prd/**`）对原型 HTML（⑥ `prototypes/`）做功能实现度验收。只读输出评价与委派建议，**不回写文件**。

### 无原型时的行为（必读）

> **这是什么**：功能性验收的对象是已生成的 HTML 原型。若仓库里还没有可对照的页原型，不能假装测过，也不能把「文件不存在」拆成几十条布局/JS 伪问题。

当工作版本下 **不存在** 任何业务页 `prototypes/{终端}/PAGE-*.html`（不含仅有 `index.html`/`map.html`）时：

1. **跳过** §2.1～2.8 的逐项对照（不编造失败项）。
2. 在「二、功能性验收」下输出 **一条** 结论：原型缺失，本轮功能性验收跳过；优先级 **中**（若用户强依赖原型交付可升 **高**）。
3. 委派建议：运行 `/lny-prd-prototype`（⑥）；若缺 `pages_prd` 且非 `ui直出`，先 `/lny-prd-page`（⑤）。
4. 若仅有壳层汇总而无业务 `PAGE-*.html`，同上视为「无业务页原型」。

### 功能性验收执行步骤

1. **先做「无原型」门禁**（见上）；不通过则结束本节。
2. **读取规格层**（②③④⑤）：
   - `ui/PAGE-*.md` / `ui/COMP-*.md`
   - `api/API-*.md` / `api_spec.md` §4
   - `feature/FEATURE-*.md`
   - `versions/{v}/pages_prd/**/*.md`（业务页；`_shell` 按桌面壳规则单独对照）

## 三、产品就绪度检查（不计 SP）

### 3.1 产品可评估链（阻塞「不可估」·虚引用）

> **虚引用规则**：不在此重复开列与 §1.4 相同的问题条目；根据 §1.4（及必要的 §1.2）结论判定 **可估 / 不可估**。  
> **计数**：汇总「共 N 个问题」时，**3.1 不计条数**（避免与文档性双计）；仅输出结论与「缺口引用 → 文档性条目」指针。

| 判定依据（文档性来源） | 不可估条件 |
|------------------------|------------|
| §1.2 / §1.4 故事与 STORY↔FEATURE | 无有效 `STORY-*`，或故事未挂 FEATURE/框架承接 |
| §1.4 FEATURE↔AC | 任一 **active** FEATURE 缺 AC 表（有数据却未挂 API/EXT 且未写「无」） |
| §1.4 Feature↔页面/接口 | active FEATURE 关联页面/接口为空且非显式「无」，或孤儿引用 |
| §1.4 非静态 PAGE↔API | 非静态页既无 API 又未说明静态 |
| §1.4 API 元数据完备 | 纳入口径的 API 缺服务对象/数据操作形态/第三方联动/响应形态，或「是」无 EXT |
